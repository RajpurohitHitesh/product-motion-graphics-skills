## Visual system

- Keep the real screenshot as the visual anchor. Place it on a brand-compatible surface with generous space and one short benefit/question headline.
- Use one primary screen or feature crop at a time. Supporting UI cards may establish context briefly, but reduce depth and perspective before the explanation starts.
- Focus attention through a crop, a subtle context dim, an outline, a connector, or a magnified detail. Use only the annotations needed to answer the current question.
- Keep actual UI labels, currency, units, graph shape, app branding, and displayed values intact. An annotation is a separate presentation layer, not permission to redraw the app into a fictitious state.
- Use a short plain-language explanation beside a complex graph or score. Keep narration captions clear of the interface labels and highlighted region.

Follow the shared 1080 × 1920 layout and safe-area guidance. For AmezPrice, use current supplied brand assets; the observed blue/light identity is provisional until exact assets are available.

## Motion grammar: original starting points at 30 fps

- Screen entry: approximately 14–22 frames with a restrained settle. A short layered reveal is optional when it helps recognition.
- Focus change: approximately 10–18 frames from the complete screen to a useful detail. Keep the crop anchored to the annotated region.
- Highlight reveal: approximately 6–10 frames, then hold according to explanation length and the actual female narration. Avoid flashing outlines and perpetual zoom.
- Show one causal/interpretive connection at a time: visible UI element → plain-language meaning → supported benefit. Return to enough surrounding context for orientation.
- Do not animate chart values or create unseen data merely to make a screenshot look active. A crop and an annotation can explain a real static graph.

Adapt pacing and motion to the supplied screenshots. These values are proposals, not measured timing from an existing clip.

## Adaptable 30-second feature story

| Time | Purpose | Screenshot treatment |
| --- | --- | --- |
| 0–3s | User question | One real feature screenshot and a concise hook |
| 3–8s | Orient | Establish the relevant screen and feature name |
| 8–21s | Explain | Two or three meaningful focus areas or concepts |
| 21–26s | Payoff | Connect the explanation to a supported use case |
| 26–30s | Next action | Clear app/feature CTA with a stable screen |

This is an example structure, not a fixed edit. Choose a different hook, crop sequence, comparison, or visual analogy when the assets and explanation call for it. Preserve the selected visual identity and actual product facts.

## AmezPrice examples

- Explain what the visible price-history graph and its displayed low/average/high values represent, with dates and currency intact.
- Introduce the displayed Deal Score without inventing its formula, promising future savings, or treating it as purchase certainty.
- Explain how Deal Radar uses the represented category/budget preferences, using current product evidence for the actual behavior.

Use one feature or a few closely related concepts per Short. A single screenshot can support a bounded explanation of visible information; it cannot establish hidden controls or all possible feature states.

## Natural female voice

Use clear, friendly female narration, beginning around 125–145 words/minute and adjusting to the language and UI complexity. Explain meaning before jargon, and pause when a new graph region or metric is highlighted. Follow the shared real-recording/AI-voice distinction. Caption the recorded speech rather than estimating timing from the script alone.

## Preview and checks

After explicit style selection, create the shared 6–8 second 540 × 960 preview showing one complete explanatory beat: screenshot → focus/annotation → understandable meaning. Include the actual female voice sample when available and label missing audio honestly.

Check that the highlight follows the screenshot's crop/scale, text remains phone-readable, captions do not cover UI, graph interpretation is accurate, and the screenshot's values are not represented as current live data without support. Do not call this a recorded live-app demo when it was composed from screenshots.
